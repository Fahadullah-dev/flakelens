# flakelens

Finds flaky tests in a pytest suite from JUnit XML history, using a Wilson
score confidence interval instead of "it failed twice so it's flaky." Runs
entirely on your machine. No CI platform account, no uploaded logs, no
dashboard login.

Exposed as an MCP server so an agent can ask "is this test suite reliable"
the same way it asks any other tool.

## why

Flaky tests account for a meaningful share of CI failures and cost teams
real diagnostic time chasing failures that were never really regressions.
Most flaky test tooling assumes you're already on a specific CI platform and
sends your test history to their service. This assumes neither: point it at
a folder of JUnit XML files you already have, or let it run your suite
locally and generate the history itself.

## the statistics

A test that failed 0 times in 3 runs is not proven stable, the sample is
just too small to say anything. A test that failed 20 times in 20 runs
isn't flaky, it's broken, flakiness means the outcome is inconsistent. This
tool keeps those cases separate instead of collapsing everything into a
single failure percentage:

- **stable-pass**: 0 failures, enough runs to be confident
- **broken**: fails every run, consistent, not flaky
- **flaky**: some runs pass and some fail
- **insufficient-data**: fewer than 5 runs, no claim is made

The failure rate reported for flaky and stable-pass tests is a 95% Wilson
confidence interval, not a raw percentage.

## install

```
pip install -e .
```

Requires `mcp>=2.0`.

## usage

Fastest path, no test execution, just reads existing JUnit XML reports:

```python
from flakelens.server import analyze_junit_history
analyze_junit_history("path/to/junit/reports")
```

Against the example history in this repo (30 simulated CI runs, generated by
`scripts/generate_demo_history.py`):

```
$ python examples/demo.py

broken         tests.test_auth::test_expired_token           30/30  ci=[0.89,1.00]
stable-pass    tests.test_auth::test_login_redirects          0/30  ci=[0.00,0.11]
stable-pass    tests.test_payments::test_currency_round       0/30  ci=[0.00,0.11]
flaky          tests.test_payments::test_webhook_retry       13/30  ci=[0.27,0.61]
stable-pass    tests.test_search::test_empty_query            0/30  ci=[0.00,0.11]
flaky          tests.test_search::test_pagination_order       2/30  ci=[0.02,0.21]
```

Slower path, actually runs your suite N times if you have no history yet:

```python
from flakelens.server import run_flakiness_scan
run_flakiness_scan("tests/", runs=20)
```

Get a ready-to-use quarantine list:

```python
from flakelens.server import suggest_quarantine
suggest_quarantine("path/to/junit/reports", threshold=0.1)
```

## tools

| tool | reads history | runs your code |
|---|---|---|
| `analyze_junit_history(directory)` | yes | no |
| `run_flakiness_scan(test_path, runs=20)` | no | yes |
| `suggest_quarantine(directory, threshold=0.1)` | yes | no |

## limitations

Only parses the JUnit XML shape pytest's `--junitxml` writer produces
(`<testcase classname name>` with `<failure>`/`<error>`/`<skipped>`
children). Jest, gradle, and other JUnit dialects use different shapes and
are not handled.

`run_flakiness_scan` executes the target project's test code directly. That
code can write files, hit a network, or touch a database, it is not
sandboxed. Point it at code you trust, same as running `pytest` yourself.
